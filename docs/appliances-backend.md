# Appliances backend — 2026-10-20

Implemented in `Back__end/app/appliances/` with separate schemas, repository, service and routes. main.py only registers the new router. Existing auth, electricity and history implementations are unchanged. The UI now loads authenticated data, saves changes, shows loading/errors and supports retry. The old prototype text was removed and the JS URL versioned.

## Behavior and API

- `GET /api/appliances?billing_month=YYYY-MM`: active usage snapshots for the current account and selected month only; never trusts a client user ID.
- `POST /api/appliances`: creates an appliance identity plus its monthly usage snapshot in one atomic Sheets batch. New entries represent separate appliances even if names match. Same physical appliance selection/reuse across months is a future UI extension; adding a new entry in another month currently creates a new identity.
- `PUT /api/appliances/{usage_id}`: edits the selected monthly snapshot only. Requires its current `revision`; stale edits return 409 and other accounts' IDs return 404. The month cannot be moved. Appliance identity/defaults remain the original captured defaults; this is not a global appliance-edit endpoint.
- `POST /api/appliances/{usage_id}/cancel`: soft cancellation, current revision required. Keeps the row with `status=cancelled`, increments revision and hides it from normal monthly lists. The appliance identity is retained. No hard-delete endpoint.
- All mutations require existing authenticated user role, same-origin JSON and a UUID `Idempotency-Key`. IDs, owner, estimates, revisions, status and timestamps are server-controlled. Identical immediate retries return the same record. Create IDs derive from owner/namespace/request key, so retrying an old creation key after later edits cannot create a duplicate. Updates/cancellations retain their last request key in the snapshot; a retry after subsequent changes must refresh and reconcile its revision.
- Response objects expose original UI field names plus `id`, `appliance_id`, nullable `estimated_kwh`, `revision`, `status` and timestamps. Clients must use the returned estimate/revision. UUIDs and timestamps are not secrets and are not used as authorization.

Required inputs: billing month, nonempty name, supported category (41 options), positive integer quantity (defaults to one). `other` requires custom category. Brand, model, nameplate watts, average watts, hours, days, monthly kWh and notes are optional. Missing numeric values persist as blank cells/null estimates, not zero. Explicit zero time/days/monthly kWh is valid. Entered watts must be positive. Days cannot exceed actual calendar-month days. Names/text are written as literal string values, never interpreted as Sheets formulas.

The service calculates with Decimal, HALF_UP to four places. Average method uses average watts/1000 × hours × days × quantity; monthly method uses per-unit kWh × quantity, discarding hours/days and average watts. Unknown sources or missing required calculation inputs produce null. Rated watts are never silently substituted for average watts. Cycling appliances require real average energy or an explicitly identified estimate; no invented duty-cycle default. Unit tests cover 64 kWh from 200 W × 8 h × 20 days × 2 appliances, and monthly energy multiplication.

## Tables and migration

Existing columns were preserved in order. Added `appliances!R1`: `category_custom` (18 columns total). Added `appliance_usage_monthly!U1:Z1`: `category_custom_snapshot`, `brand_snapshot`, `model_snapshot`, `status`, `revision`, `request_id` (26 columns). Native table ranges were expanded and existing category dropdowns extended to the UI's categories; original types/validation for other columns were retained. CSV headers and the schema manifest were updated. Both production tables were empty before migration; no existing data rows were rewritten.

Repository uses thread-local HTTP sessions with connect/read timeouts, one batch read of both worksheets, and one atomic batch write for identity + usage + native table range changes. Grid grows when required. Schema mismatch stops writing. Numeric estimate cells are actual numbers; unknown inputs are blank. No changes were made to users, electricity_records, user_settings or ai_reports.

## Redis, I/O and limits

The new feature shares the existing bounded Redis connection pool and renewable token-safe lock implementation, with its own namespace derived from spreadsheet and worksheet names. A 30-second coherent cache holds both datasets; warm monthly reads avoid appliance Sheet I/O. A cold cache coalesces concurrent reads. Writes take the same distributed lock, read fresh source data, check ownership/revision/idempotency, invalidate before committing, then publish the updated cache. Cache refresh failure after confirmed persistence still returns success. Redis lock failure fails closed. The lease coordinates application workers, not manual edits or unrelated Sheets writers.

Google Sheets remains quota-limited and writes are serialized. Both datasets are cached in full and filtered per request, so memory/CPU grow with data volume. Authentication still reads the current user from Sheets each request, preserving immediate revocation but limiting real concurrency. A database migration and separate auth-cache policy would be needed for substantial production scale. No claim of large-production capacity follows from the two-record synthetic benchmark.
