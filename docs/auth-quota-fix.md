# Shared authentication read quota fix — 2026-10-21

The supplied production log reports Sheets API 429 during `get_current_user -> find_user_by_id -> get_all_users -> get_users_worksheet -> open_by_key`. This is a shared service-account read quota, not evidence of cross-account data leakage. Each protected page/API reconstructed spreadsheet/worksheet metadata and read users again; two browsers opening several pages therefore exhausted the same quota. Data-sheet Redis caches did not remove this auth-stage bottleneck. Empty-data accounts still pay authentication I/O.

The user explicitly approved a **10-second role/status cache**. `app/services/auth_user_cache.py` now provides the lookup used by both API and page authentication dependencies. It reads users through a thread-local, timeout-bounded HTTP client with a direct A:L values request (one Sheets read, no per-request spreadsheet/worksheet metadata calls), projects only user_id/full_name/email/phone/role/status and caches that snapshot for 10 seconds under a spreadsheet/users-tab-specific namespace. Password hashes, OAuth identifiers, JWTs and session IDs are not included in the new cache. Profile fields remain protected internal data, not publicly exposed.

Concurrent misses use the existing renewable Redis lock to coalesce refreshes. A missing user triggers a source refresh so a newly registered account is not rejected solely because it was absent from the older snapshot. Blank/duplicate identities fail closed. On source 429 a 10-second cooldown prevents repeated refresh attempts. Expired auth data is never used as fallback when the source is unavailable. Other application writes/login uniqueness checks remain uncached and unchanged.

JWT signature/expiry, Redis session existence and user/role consistency are still checked per request. Logout/revoked sessions take effect immediately even if user data is cached. Direct Sheets role/status/account deletion changes can take the approved 10-second window to be observed; application/network latency may add refresh time. There is no current admin mutation API requiring an invalidation hook; future role/status/profile mutation endpoints must invalidate the snapshot after their successful write, or enforce the same documented window. Existing immediate-DB-read statements in earlier feature reports describe the earlier implementation and are superseded by this change.

`app/core/storage_errors.py` adds generic 503 + Retry-After handling for otherwise unhandled gspread/Redis errors. Auth lookup failures return the same bounded retry behavior and do not delete a valid session or pretend an account is empty. No raw credential/URL/error details are exposed to clients. A real outage/quota exhaustion can still require retry; this fix reduces requests rather than promising unlimited Google API capacity.

## Verification

- 103 Python tests passed including prior feature/auth regression tests and seven new auth-cache tests. New cases cover 80 simultaneous lookups for two users with one source refresh, TTL/status refresh, no stale fallback, missing-new-user refresh, source-429 cooldown, mixed API isolation across two separate sessions, replay of the old cookie after logout, denial after account status refresh, generic failure handling, and direct values reads without metadata reconstruction. Snapshot contents are checked to exclude password hashes.
- Synthetic k6: two independent fixture accounts, 20 VUs, four API paths per iteration (me/history/appliances/analysis), 9,677 HTTP requests in ~16.4 s, ~592 requests/s overall, p95 mixed-page request 43.89 ms. All 19,337 checks passed, zero unexpected HTTP errors, **two auth source refreshes** over the 15-second workload. Session/JWT/Redis/cache logic is real; external repositories are synthetic. Dataset is small, not a production capacity estimate.
- Real Sheets: two isolated accounts, four mixed-page iterations at two VUs without pacing sleeps; 24 total HTTP requests including registration/login/seed/logout, all 32 checks passed, zero unexpected errors/429 in this run. Mixed-page p95 1.39 s, median 4.39 ms; cold data reads and cache hits are mixed, so this small sample is not directly comparable to a single-endpoint benchmark.
- The first version of the two-account k6 harness used a shared cookie jar plus explicit Cookie headers and failed its isolation assertions. Independent request-cookie overrides fixed the harness; no production account-data isolation change was required. Separate-session Python tests passed throughout. Final results above are from the corrected harness.
- Live fixture writes used only disposable hidden test tabs with a separate Redis/network. No production users/bills/appliances were written. Fixtures and test containers/networks were removed afterward. Raw summaries/logs are ignored under tmp/k6/auth-cache-*.json/log.
